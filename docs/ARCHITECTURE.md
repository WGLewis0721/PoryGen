# Architecture

## Overview

```
Browser (React/Vite SPA)
   │  supabase-js (publishable key; RLS-scoped)
   ▼
Supabase
   ├─ Postgres (profiles, repositories, scans, scan_findings,
   │             provenance_events, billing_customers, billing_events)
   │             — Row Level Security on every table
   ├─ Auth (email/password; session in localStorage via supabase-js)
   └─ Edge Functions (Deno)
        ├─ scan-repository     — GitHub ingestion + scanner + license check
        ├─ create-checkout     — Stripe Customer + Checkout Session
        ├─ stripe-webhook      — verified, idempotent webhook ingestion
        └─ billing-diagnostics — non-secret config readout

External:
  GitHub REST API (api.github.com, raw.githubusercontent.com) — repo ingestion
  npm registry / PyPI JSON API — dependency license lookups
  Stripe API — Customers, Checkout Sessions, webhook events
```

## Frontend

Vite + React + TypeScript + React Router. No server-side rendering — a static SPA
talking directly to Supabase. Structure:

```
src/
  components/       shared UI: BitCritter, AppShell, MarketingNav, Footer, PolicyBadge
  features/
    auth/           AuthContext, sign-in/up pages, ProtectedRoute
    marketing/      landing, product, pricing, enterprise, docs pages
    dashboard/      authenticated overview
    repositories/   feed-a-repo, repository list
    scanner/        scan progress + results (one page, driven by scan.status)
    findings/       finding detail
    provenance/     dual-column ledger (event stream + attestation/chain)
    reports/        evidence bundle export + print report
    billing/        Stripe status, diagnostics, success
    settings/       profile
  lib/              supabaseClient, typed DB row shapes, api.ts (all Supabase calls)
  styles/           design tokens, global reset, layout chrome, app chrome
```

Design tokens (`src/styles/tokens.css`) implement the Hardware Brutalism × Cybernetic
Familiar system: `--pg-base` (deep slate), `--pg-structure` (chalk silver), `--pg-accent`
(acid chartreuse), zero border-radius, JetBrains Mono throughout.

## Supabase

Migrations (`supabase/migrations/`) are applied in order; see
[DATA_MODEL.md](DATA_MODEL.md) for the schema and [SECURITY.md](SECURITY.md) for the RLS
policy set. `profiles` is populated by a trigger on `auth.users` insert
(`handle_new_user`, `SECURITY DEFINER`, `EXECUTE` revoked from `anon`/`authenticated` so
it can only run as the trigger — flagged and fixed via the Supabase security advisor).

## GitHub ingestion

`supabase/functions/scan-repository/github.ts` is the entire SSRF boundary: it only ever
constructs URLs against `api.github.com` and `raw.githubusercontent.com`, built from an
owner/repo pair that's been regex-validated after parsing (never a raw user-supplied
URL passed straight to `fetch`). Ingestion limits (40 files, 200 KB/file, 2 MB total,
vendor/generated directories skipped) are enforced before any file content is read into
memory.

## Scanner

Three layers, all in `packages/provenance-core/src/scanner`:

1. **Normalize** — either `lexicalNormalize.ts` (dependency-free, runs everywhere
   including the edge function) or `treeSitterNormalize.ts` (real tree-sitter grammars,
   Node-only, used for tests and Lattice fixture generation). See
   [SCANNER.md](SCANNER.md) for exactly which one runs where and why.
2. **Fingerprint** — `winnow.ts`, the real Winnowing algorithm over normalized token
   k-grams.
3. **Compare** — `corpus.ts` (structural similarity against a bundled reference corpus)
   and `license.ts` (manifest/lockfile parsing + SPDX policy mapping).

`scan-repository`'s own copy of this logic under `_shared/` is generated by
`scripts/sync-vendored-copies.mjs` from the same source — never hand-forked.

## Provenance

`packages/provenance-core/src/provenance/events.ts` implements the canonical event
shape, the SHA-256 hash chain, and in-toto statement construction. `sigstore.ts` is the
signing boundary — see [PROVENANCE.md](PROVENANCE.md). `classifier.ts` is the VS Code
extension's edit-shape heuristic, shared (as a vendored copy, for CommonJS
compatibility) with `packages/vscode-extension`.

## Stripe

`create-checkout` creates/reuses a Stripe Customer (service-role write to
`billing_customers`, which has no client-facing write policy) and a Checkout Session for
the PoryGen Pro Scan Pack, tagging both with `porygen_user_id`, `porygen_plan`, and — when
configured — `apex_customer_id`. `stripe-webhook` verifies the Stripe-Signature header by
hand (HMAC-SHA256, no SDK dependency for one check) and persists events idempotently via
a unique constraint on `stripe_event_id`. See [STRIPE_SETUP.md](STRIPE_SETUP.md) and
[APEX_DOGFOOD.md](APEX_DOGFOOD.md).

## Future APEX entitlement boundary

PoryGen's demo billing state is local and display-only — it does not implement a second
production entitlement ledger. The seam is `src/lib/entitlements.ts` (see
[APEX_DOGFOOD.md](APEX_DOGFOOD.md)): a `LocalDemoEntitlementProvider` today (a
`localStorage`-backed display counter, not a security boundary — actual scan
authorization is Supabase RLS), with an `ApexEntitlementProvider` stub that throws until
APEX's own SDK and credentials are deliberately wired in. PoryGen never fabricates that
integration.
