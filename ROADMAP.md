# PoryGen Roadmap

> **Product:** source-similarity and likely-source discovery for code  
> **Company:** Gray Matter  
> **Current stage:** live multi-input MVP + early PoryGen Engine  
> **Core question:** **Does this code meaningfully resemble code that exists somewhere else, and where might it have come from?**

## Product thesis

PoryGen checks code against indexed public source and shows evidence when meaningful similarity is found.

The code may have been:

- written by hand;
- copied or adapted from GitHub, a blog, a forum, documentation, or another public source;
- produced with AI assistance;
- fully generated by an AI model or coding agent;
- inherited from another developer;
- or created through a mixture of all of the above.

PoryGen does **not** depend on knowing how the code was created. The artifact is what matters.

The product promise remains:

**Move fast. Keep it yours.**

### Product rules

1. The core product is source-match discovery, not AI detection.
2. Do not narrow the audience to a particular model, IDE, coding agent, or app builder.
3. GitHub, ZIP, folders, MCP, CLI, CI, and APIs are input surfaces, not separate products.
4. Default to conservative reporting and explicit abstention.
5. Never imply exhaustive internet coverage.
6. Never present similarity as proof of copying, infringement, plagiarism, originality, or AI authorship.
7. License metadata, resolution suggestions, reports, monitoring, and compliance workflows are downstream value from a source finding; they do not redefine the core problem.
8. Source should remain transient unless persistence is deliberately required for a customer-facing feature.
9. Keep matching and proprietary ranking server-side.
10. One useful first scan should remain available without account setup.
11. Corpus collection, indexing, rarity analysis, retrieval, ranking, verification, source metadata, and related intelligence ship under one technology name: **the PoryGen Engine**.

## Current scan bounds

Common source budgets:

- **150 matched files**
- **100 KB per source file**
- **2 MB accepted source per scan**
- bounded request-time processing

ZIP-specific bounds:

- **2.9 MB compressed ZIP**
- **1,000 archive entries**
- **10 MB declared/expanded archive budget**
- nested archives ignored rather than recursively unpacked

The server remains authoritative for all limits.

## Current product limitations

- connected private GitHub repositories are not supported yet;
- JS / TS / Python only;
- synchronous bounded scan path;
- production serves only a subset of the existing offline corpus;
- GitHub review/dismiss history is browser-local;
- uploaded-project results intentionally disappear when the page/session is gone;
- Source Match Report exists in open PR #20 but is not yet merged/deployed; the current implementation is a local standalone HTML/printable export, not durable hosted sharing;
- no MCP server;
- no CLI;
- no GitHub App;
- no automatic push/PR scanning;
- no GitHub Check Runs;
- no team/workspace controls;
- no production customer billing enforcement;
- no async large-repository worker.

These are growth constraints, not reasons to reopen the matcher without a concrete production failure.

## Phase 2 — Source Match Report

**Status: IN FLIGHT — IMPLEMENTED IN PR #20, NOT MERGED/DEPLOYED**

**Goal:** Turn one completed scan into a clean artifact that answers the source-match question without forcing someone to re-read the scan UI.

The name is **Source Match Report**, not “compliance report,” “originality certificate,” or “AI report.”

### Report contents

- [x] project/source label and scan timestamp;
- [x] what input was scanned;
- [x] coverage and completeness;
- [x] strong findings;
- [x] possible/common findings where useful;
- [x] affected file and matched lines;
- [x] possible public source;
- [x] source/license/version metadata already known by the Engine;
- [x] side-by-side or compact evidence;
- [x] exclusions;
- [x] dismissed/reviewed findings and notes where available;
- [ ] explicit limitations: indexed-source coverage, not proof of copying/originality, not legal advice.

### Privacy rules

- [x] Do not persist uploaded source merely to create a report.
- [x] Prefer a downloadable/exportable report first.
- [x] If private sharing is later added, persist only what is deliberately required and make the retention boundary explicit.
- [x] Do not call the output a certificate.

### Implementation status

PR #20 builds the report locally in the browser as a self-contained HTML file with browser Print/PDF support. It includes scope, completeness, exclusions, strong and possible findings, matched lines, pinned source/license/version metadata, compact evidence, current review/dismissal decisions and explicit limitations. The implementation adds no report API or hosted persistence.

Focused report tests and the production build passed on the PR branch. Browser print/PDF output has not yet been visually verified. Because PR #21 landed afterward, PR #20 must be reconciled with current main before merge/deploy.

### Exit criterion

A developer can hand someone a clear artifact answering:

> **What in this code matched public source, where did it match, and what evidence did PoryGen see?**

## Phase 3 — PoryGen MCP

**Status: NOT STARTED**

**Goal:** Let coding agents call the same PoryGen Engine while code is being written.

PoryGen should work with any compatible agent/model workflow rather than being designed around one vendor.

Candidate tools:

- porygen_scan_files
- porygen_scan_workspace
- porygen_check_diff
- porygen_explain_finding
- porygen_get_source
- porygen_rescan

### Rules

- same Engine;
- same conservative finding semantics;
- no AI-authorship score;
- no agent-specific matcher;
- results remain evidence, not accusations.

### Exit criterion

An agent can generate or modify code, ask PoryGen whether the changed code materially resembles indexed public source, and receive actionable evidence.

## Phase 5 — PoryGen Engine scale-up

**Status: IN PROGRESS**

**Goal:** Search a materially larger public-code universe without changing the customer-facing question.

### Next engine work

- [ ] Serve substantially more of the existing 50k-file corpus.
- [ ] Move beyond a Vercel-bundled corpus pack to a dedicated retrieval/index layer.
- [ ] Scale toward hundreds of thousands and then millions of source files.
- [ ] Strengthen likely-canonical / likely-upstream source ranking.
- [ ] Preserve exact package/version/license/source provenance.
- [ ] Add more versions where version identification materially improves evidence.
- [ ] Expand beyond npm/PyPI when it produces meaningful coverage gains.
- [ ] Deliberately broaden public-source and license diversity.
- [ ] Keep corpus-wide rarity as a core ranking signal.
- [ ] Evaluate heavier parsing only for ambiguous candidates.
- [ ] Benchmark when reporting logic changes or production evidence identifies a concrete accuracy issue.

### Exit criterion

PoryGen searches a broad public-code universe with low latency, conservative attribution, useful likely-source ranking, and honest coverage disclosure.

## Success definition

PoryGen is succeeding when a developer can say:

> “I gave PoryGen my code, it showed me what meaningfully resembled public source and where it may have come from, and I could inspect the evidence.”

The business succeeds if that core source-discovery value is strong enough that developers later choose reports, agent/CLI integration, larger coverage, continuous monitoring, history, collaboration, and other paid capabilities.
